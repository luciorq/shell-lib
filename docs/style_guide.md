# Shell-lib Style Guide and Design Patterns

This document describes the coding style and the design patterns used across
the functions in [`lib/`](../lib) and the generated programs in
[`bin/`](../bin).
It is both descriptive (what the code does today) and normative
(what new and refactored code should do).

> Some functions require **Bash >= 4.4**.
> This baseline is load-bearing: it is what makes `"${@}"` safe under
> `set -o nounset`, and enables `mapfile`, `declare -A`, `${var,,}`,
> `${var@Q}`, and negative substring offsets.

The one deliberate exception to everything below is
`lib/force-xdg-basedirs.sh`, which is an environment file meant to be sourced
by interactive shells and does not follow library conventions.

---

## 1. Goals and philosophy

1. **Composable building blocks.** Every file in `lib/` only declares
  functions; sourcing a file must have no side effects. Standalone programs
  in `bin/` are generated by composing functions along the dependency graph
  (see [`dependency_graph.md`](./dependency_graph.md)).
2. **Explicit over implicit.** Commands are resolved to absolute paths before
  use, variables are always expanded with `${var}` braces, and defaults are
  spelled out with `${1:-default}`.
3. **Interactive-shell safe.** Functions are sourced into login shells, so
  they must never `exit`, never leave `set -e`/`set -x` enabled, and never
  leak variables into the caller's namespace.
4. **Portable across devices and OSs** (Linux glibc/musl, macOS, WSL, MSYS2),
  granted a modern Bash.
  Anything GNU-only or BSD-only must be feature detected or replaced.
5. **Avoid the classic pitfalls** catalogued at
  [BashPitfalls](https://mywiki.wooledge.org/BashPitfalls): no parsing of
  `ls`, no `for` over lines, no unquoted expansions, no `which`.

## 2. File conventions

- One topic per file; the file name matches the main public function
  (`unpack.sh` -> `unpack`) or the topic (`slurm_lib.sh`).
- Names are lowercase `snake_case` with the `.sh` extension. Do not use
  dashes in file or function names.
- Suffix conventions: `*_pure` for pure-Bash reimplementations of external
  tools; `*_fun` for wrappers that shadow/extend an existing command
  (`cd_fun`, `ssh_fun`); `*_lib` / `*_utils` / `*_tools` for topical
  collections. Prefer `*_lib` for new topical collections.
- Every file starts with:

  ```bash
  #!/usr/bin/env bash
  # shellcheck shell=bash
  ```

  The shebang exists only so editors and ShellCheck pick the right dialect;
  library files are sourced, never executed.
- Files never run code at the top level (no `set`, no `export`, no command
  invocations), only comments and function declarations.

## 3. Function conventions

### 3.1 Canonical skeleton

```bash
# One-line description of what the function does.
# + Continuation lines of a comment start with `# +`.
# @param $1 <NAME>  description; Default: value
function my_function () {
  \builtin local _usage;
  _usage="Usage: ${FUNCNAME[0]} <ARG> [<OPTIONAL_ARG>]";
  if [[ "${1:-}" == "-h" || "${1:-}" == "--help" ]]; then
    \builtin echo -ne "${_usage}\n";
    \builtin return 0;
  fi
  \builtin local input_arg;
  \builtin local grep_bin;
  input_arg="${1:-}";
  if [[ -z ${input_arg} ]]; then
    exit_fun "Invalid execution.\nUsage: ${_usage}";
    \builtin return 1;
  fi
  grep_bin="$(require 'grep')";
  if [[ -z ${grep_bin} ]]; then
    \builtin return 1;
  fi
  # ... body ...
  \builtin return 0;
}
```

Rules:

- `function name () {` - with the `function` keyword, a space before `()`,
  and the opening brace on the same line.
- Two-space indentation. Terminate simple commands with `;`. Apply this
  consistently within a file.
- Public API functions get a plain name; internal helpers are prefixed with
  `__` (double underscore) and are not expected to be called by users or exposed
  in `bin/`.
- Loop and throwaway variables are prefixed with `_` (`_arg`, `_pkg`,
  `_host_name`).
- Use `${FUNCNAME[0]}` in `_usage` strings. `${0}` is **not** the function
  name, in a sourced function it expands to the shell binary name.
- End every function with an explicit `\builtin return 0;` (or the
  appropriate status).

### 3.2 `\builtin` hardening

Builtins are invoked as `\builtin local`, `\builtin echo`, `\builtin cd`,
etc. The `\` defeats alias expansion and `builtin` defeats function
shadowing, so library code behaves the same even inside heavily customized
interactive shells.

- Apply it to *every* builtin call in library code.
- Never call an external command bare. Either resolve it first
  (section 4) or, for a one-off in bootstrap code, use the `\cmd`
  alias-bypass form deliberately and sparingly.

### 3.3 Locals: declare, then assign

```bash
\builtin local cmd_bin;
cmd_bin="$(which_bin 'curl')";
```

Declaration and command-substitution assignment are separate statements
because `local x="$(cmd)"` masks the exit status of `cmd`. Group all `local`
declarations at the top of the function. **Every** variable assigned inside a
function must be declared `local`, leaking globals is a bug.

### 3.4 No `set -e` / `set -u` inside library functions

Library functions run inside the user's interactive shell, so they must not
flip global shell options. Robustness comes from:

- expanding every positional parameter with a default: `${1:-}`, `${2:-value}`;
- checking required arguments explicitly and returning `1`;
- checking resolved binaries for emptiness before use.

`set -o xtrace` may be enabled only behind the debug convention, and must
always be turned back off:

```bash
\builtin local _debug_var;
_debug_var="${DEBUG:-false}";
if [[ ${_debug_var} == true ]]; then
  \builtin set -o xtrace;
fi
# ... body ...
if [[ ${_debug_var} == true ]]; then
  \builtin set +o xtrace;
fi
```

Standalone scripts in `bin/` (which own their process) may use
`set -o errexit -o nounset -o pipefail` in their entry-point preamble.
The `appbuilder` constructor is the right place for inserting this header,
not the sourced functions.

## 4. Design pattern: command resolution

The backbone of the library is "resolve first, then invoke":

```bash
curl_bin="$(which_bin 'curl')";      # optional dependency
tar_bin="$(require 'tar')";          # hard dependency
fun_name="$(require_fun 'unpack')";  # dependency on another lib function
```

- **`which_bin NAME`** - pure-Bash `PATH` walk. Prints the absolute path of
  the first match, or the empty string. Never errors. Use it for *optional*
  tools and implement a fallback for the empty case.
- **`require NAME [CHECK_ARGS...]`** - resolves like `which_bin` but calls
  `exit_fun` when the tool is missing (optionally validating that the tool
  runs, e.g. `require 'ssh' '-V'`). Use it for *hard* dependencies.
- **`require_fun NAME`** - same contract for shell functions.

Invocation is always through the resolved variable, quoted:

```bash
"${tar_bin}" -C "${dir_output}" -xzf "${zip_path}";
```

**Important caveat:** `require` is almost always called inside `$(...)`.
Command substitution runs in a subshell, so the abort raised by `exit_fun`
kills only the subshell: the caller *continues* with an empty variable.
Therefore:

> After `x_bin="$(require 'x')"`, treat an empty `${x_bin}` as "dependency
> missing" and `return 1`. The `-z` check is mandatory, not defensive noise.

Preference chains (e.g. `micromamba` > `mamba` > `conda`, or `gsed` > `sed`,
`bat` > `batcat` > `cat`) are expressed as successive `which_bin` calls with
`-z` checks, encapsulated in a `get_*_bin` function when reused
(`get_conda_bin`).

## 5. Design pattern: error handling with `exit_fun`

`exit_fun 'message'` prints the message to stderr and raises a
`${var:?}`-style abort that unwinds the *whole function call stack* without
killing an interactive shell. Because that abort does not propagate out of
subshells (see the caveat above), the calling convention is:

```bash
exit_fun "'${cmd_str}' executable not found in '\${PATH}'";
\builtin return 1;
```

- **Always** pair `exit_fun` with an explicit `\builtin return 1;` on the
  next line. Never let control fall through after it.
- Error messages quote the offending value in single quotes:
  `'value'`. Command names in prose use the same convention
  (`'rsync' is not installed`). Do not mix in `` `backticks `` or `{braces}`,
  pick `'...'` everywhere.
- Warnings that do not abort go straight to stderr:
  `\builtin echo >&2 -ne "...\n";`.

## 6. Design pattern: returning values

Functions "return" strings by printing to stdout and are consumed with
command substitution:

```bash
platform_str="$(get_conda_platform)";
```

- Print data with `\builtin printf '%s' "${value}"` (no trailing newline for
  single values consumed by `$(...)`; command substitution strips it anyway).
  Do **not** use `echo -ne "${value}"` for data: `-e` reinterprets any
  backslash sequences contained *in the data*, and a value of `-n` would be
  swallowed as an option. `echo -ne` is acceptable only for literal,
  hand-written format strings (`\builtin echo -ne "Done.\n"`).
- List-returning functions print one item per line
  (`\builtin printf '%s\n' "${arr[@]}"`) and are consumed with
  `\builtin mapfile -t out_arr < <( ... )`.
- Boolean-returning functions print the literal strings `true` / `false`
  (`is_available`, `is_compressed`, `sudo_check`) so callers can write
  `if [[ $(sudo_check) == true ]]`. Functions that only signal
  success/failure use return codes instead.

## 7. Design pattern: configuration

Machine- and user-specific data live in YAML files, not in code:

- `parse_yaml FILE [KEY...]` extracts values, with a backend preference chain
  `yq` (mikefarah/go) > `ruby` > `python` + PyYAML.
- `get_config FILE_BASENAME [KEY...]` looks the file up under
  `${XDG_CONFIG_HOME}/.../vars/*.y(a)ml`; `get_config --priv ...` reads from
  the private config directory resolved by `get_config_path`.
- Anything site-specific (SLURM partition names, host aliases, package
  lists, allowed sync hosts) belongs in config, with a generic default in
  code: `partition_name="${1:-$(get_config slurm default_partition)}"`.

XDG base directories are always referenced with an inline fallback:
`${XDG_CONFIG_HOME:-${HOME}/.config}`, `${XDG_DATA_HOME:-${HOME}/.local/share}`,
`${XDG_CACHE_HOME:-${HOME}/.cache}`.
Never assume the variables are set.

## 8. Design pattern: lib -> bin composition

`bin/` programs are generated from `lib/` functions by the `appbuilder` using
the function dependency graph.
Consequences for library code:

- A function must reference other library functions **only by direct call**
  (that is what the graph tracks). Dynamic dispatch through `eval` or
  variables hides dependencies and breaks the build.
- Keep functions free of top-level state so any subset of files can be
  concatenated into a standalone script.
- The generated scripts must be runnable via
  `curl ... | bash`, so nothing may assume the repository layout at runtime.

## 9. Quoting and expansion rules

- Quote **every** expansion in command arguments: `"${var}"`, `"${arr[@]}"`,
  `"$(cmd)"`. Inside `[[ ]]`, quoting `${var}` is optional but the regex
  operand of `=~` must be an *unquoted variable* holding the pattern:

  ```bash
  \builtin local int_regex;
  int_regex='^[0-9]+$';
  [[ ${value} =~ ${int_regex} ]]
  ```

  Never interpolate untrusted text directly on the right side of `=~`; for
  literal-string matching use `==`, not `=~` (`=~` treats `.`/`+`/`(` as
  regex metacharacters, this is how `which_bin 'g++'`-style bugs happen).
- Pass argument lists as `"${@}"`. Given the Bash >= 4.4 baseline, `"${@}"`
  is safe with zero arguments even under `nounset`, do **not** write
  `"${@:-}"`, which injects a single *empty argument* when none were given
  (turning `ls "${@:-}"` into `ls ''`, an error).
- Build variable-length option lists as arrays, never as strings that rely
  on word splitting:

  ```bash
  \builtin declare -a key_arg_arr;
  key_arg_arr=();
  if [[ -n ${key_path} ]]; then
    key_arg_arr+=('-i' "${key_path}");
  fi
  "${ssh_bin}" "${key_arg_arr[@]}" "${host_str}";
  ```

  An empty array expands to zero words under `"${arr[@]}"`, this is the
  portable replacement for the unquoted `${flags}` idiom.
- `eval` is forbidden except for its two legitimate jobs here: applying
  environment exports produced by trusted tools
  (`eval "$(zoxide init bash)"`, conda activation hooks) and the documented
  `extra_cmd` escape hatch in `install_apps` (whose input is the user's own
  config file). Never `eval` to build a command line, use arrays.
- Read lines with `mapfile -t arr < <(cmd)`; iterate files with globs
  (`for _f in "${dir}"/*; do`), never by parsing `ls`.
- Use `--` before positional operands of external commands that may start
  with `-` (`rm -- "${path}"`, `cd -- "${dir}"`).
- Arithmetic uses `(( ))`; comparisons in `[[ ]]` use `-eq`/`-gt` for
  numbers and `==`/`!=` for strings. Prefer `[[ -z ${x} ]]` over
  `[[ ${x} == "" ]]`.
- Prefer parameter expansion over `sed`/`awk`/`cut` for simple string
  surgery: `${var%.gz}`, `${var##*/}`, `${var,,}`, `${var//x/y}`. When
  stripping a *suffix*, anchor it (`${name%.gz}`), never use substring
  replacement (`${name/.gz/}` matches anywhere in the path).

## 10. Portability rules

The claim "portable given modern Bash" translates to these concrete rules:

- **Detect the platform with Bash variables first, `uname` second**:
  `get_os_type` (normalized, lowercase: `linux`, `darwin`), `get_os_arch`,
  `get_hostname`. Never branch on raw `${OSTYPE}` outside those helpers.
- **`sed -i` is not portable.** GNU wants `-i`, BSD/macOS wants `-i ''`,
  each dialect errors on the other's form. In-place edits must either go
  through a helper that branches on `get_os_type`, or (preferred) write to a
  temp file from `create_temp` and move it into place.
- **No GNU-only regex escapes in `sed`/`grep`**: `\s`, `\w`, `sed -r`.
  Use `[[:space:]]`, `[[:alnum:]_]`, and `sed -E` (accepted by both GNU and
  BSD since ~2010).
- **`stat`, `df`, `date`, `ls`, `mktemp` flags differ across GNU/BSD.**
  Any use beyond the POSIX intersection needs an OS branch (e.g. `stat -c`
  vs `stat -f`; `df -T` vs `df -Y`; `mktemp --suffix` is GNU-only, put the
  distinguishing text in the `-t` template instead).
- **Linux-only tools need a macOS fallback or an explicit guard**: `ss`
  (use `lsof -i`/`netstat` on darwin), `nproc` (`sysctl -n hw.ncpu`),
  `timeout` (`gtimeout` from coreutils), `getent` (`dscl`), `useradd`
  (`sysadminctl`). When no fallback is implemented, fail early with
  `exit_fun` and a message that names the platform gap.
- **Prefer pure-Bash implementations** where they exist (`dirname_pure`,
  `head_pure`, `cat_pure`, `sleep_pure`, `which_bin`), they sidestep the
  GNU/BSD problem entirely.
- **Never disable TLS verification** (`curl --insecure`,
  `wget --no-check-certificate`) as a portability workaround. Downloads use
  `curl --proto '=https' --tlsv1.2 -fsSL`; machines with broken CA stores
  get fixed, not trusted less.
- Normalize collation and tool language where output is parsed:
  `LC_ALL=C "${sort_bin}" ...`.
- Redirection style: use `> /dev/null 2>&1` (portable, explicit order); do
  not mix in `&>` and `2> /dev/null > /dev/null` variants.

## 11. Safety rules

- Destructive operations go through `rm_safe`, which refuses to remove a
  curated list of protected roots. Interactive confirmations
  (`read -r -p "... [y/N] "`) guard anything that pushes force-updates or
  cancels other users' work.
- Never `rm -rf "${dir}"/.*`, the `.*` glob matches `..`. Use
  `"${dir}"/{.[!.],..?,}*` patterns or `find`.
- Quote-and-check before interpolating user input into code strings passed
  to other interpreters (R, Python, Ruby, `sg`, `ssh`). Where interpolation
  is unavoidable, validate with an anchored regex first
  (`^[0-9]+$`, `^[A-Za-z0-9_.-]+$`).
- Temp files come from `create_temp` (which wraps `mktemp -d -t`), never
  hand-built `/tmp` paths.

## 12. Testing and linting

- Every file must pass `shellcheck` clean (directives allowed with a
  justification comment), `just lint` runs it across `lib/`.
- Function behavior is tested with Bats (`tests/test-*.bats`); generated
  executables with pytest (`tests/test_app_*.py`).
- New functions should ship with at least a smoke test asserting the happy
  path and the missing-dependency path.

## 13. Documentation conventions

- Comment block above each function: one-line summary, `# +` continuation
  lines, `@param` / `@return` tags for non-obvious signatures.
- `TODO: @luciorq <text>` marks known debt. Dead code should be deleted, not
  commented out, git history preserves it. (Several files currently violate
  this; treat large commented blocks as removal candidates.)
